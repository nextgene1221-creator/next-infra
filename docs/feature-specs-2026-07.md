## ① 志望校診断AI

**目的**: 生徒の模試結果・学力推移・志望校から、AIが合格可能性や受験校の当たり/挑戦度を診断し、講師の進路指導を補助する。

**現状（既存の関連実装）**:
- `MockExamResult`: `overallDeviation`（偏差値）/ `overallScore` / `judgment`（A〜E）/ `subjects`（科目別 JSON）/ `gradeLevel`。
- `Student`: `firstChoiceSchool` / `desiredFaculty` / `examSubjects` / `considerRecommendation` / `track`（文理）/ `graduationYear`。
- **AI基盤は未導入**（`package.json` に AI SDK なし）。大学側の偏差値・判定基準データも無し（→⑤）。

**仕様案**:
- **AI連携**: Claude API（`@anthropic-ai/sdk`）または Vercel AI SDK 経由。モデルは最新Claude系。認証は `ANTHROPIC_API_KEY`（または Vercel AI Gateway）。**構造化出力**（判定・可能性・根拠）で受ける。
- **入力**: 生徒プロフィール（学年・文理・志望校/学部・受験科目・推薦検討）＋直近模試（偏差値推移・科目別）。
- **出力**: 志望校（群）ごとに「挑戦／実力相応／安全」の位置づけ、合格可能性の所見、弱点科目と推奨アクション。
- **保存**: 診断結果を残すなら新モデル `AspirationDiagnosis`（studentId / inputSnapshot JSON / result JSON / createdById / createdAt）。
- **UI**: 生徒詳細（`/students/[id]`）に「志望校診断」パネル or ボタン。生成は admin/teacher。
- **要確認**:
  1. 診断は**AIの推論のみ**か、大学ごとの偏差値/判定テーブル（⑤）を併用した半定量か。
  2. **生徒本人に見せる**か（進路面談の材料として講師のみか）。
  3. 結果を保存・履歴管理するか、都度生成の使い捨てか。
  4. 免責表示の要否（「参考値」明記）。

**オーナー記入**：基本生徒が使う想定ですが、生徒がAIに相談できる場をシステム内に作る想定です。プロフィールなどの情報は当然入力されているような形を想定しています。

## ② 出願戦略ジェネレータ

**目的**: 併願パターン・入試方式（一般/共通テスト利用/推薦）・日程を踏まえた出願プランをAIが提案する。

**現状**:
- `Student.considerRecommendation` / `examSubjects` / `track` / `firstChoiceSchool`。
- 大学の**入試日程・方式・受験料データは無し**（→⑤が前提）。

**仕様案**:
- ①と同じAI基盤を共用。**入力**=志望校リスト＋模試＋受験科目＋推薦可否＋予算感（任意）。**出力**=出願校の組み合わせ案（本命/併願/滑り止め）、方式の割り当て、**日程衝突チェック**、受験料概算、想定リスク。
- **保存**: `ApplicationStrategy`（studentId / result JSON / createdAt）で版管理も可。
- **UI**: 生徒詳細 or 進路面談モーダル内。
- **要確認**:
  1. **①と独立機能か、統合**（「診断→戦略」を1フローに）か。→ 受験支援クラスタとして一体設計を推奨。
  2. 入試日程・方式・受験料データの**入手元**（⑤で手動登録 or 外部取得）。
  3. 出力の粒度（校数上限、方式ごとの詳細度）。

**オーナー記入**：はい、大まかあっています。基本は予算情報を元に沖縄からの移動費や宿泊費も計算します。受験の度に沖縄から出るわけではなく、ほぼまとめて行くからです。

## ③ 出退席のQR導線変更

**現状フロー**:
- `/study-room`（admin/teacher 限定）が**校舎ごとに静的QR**を表示。QRの中身は `{origin}/study-room/check-in?campus=<code>`（`CheckInQR.tsx`）。掲示・印刷して入口に貼る運用。
- 生徒がスマホでスキャン → `/study-room/check-in?campus=X` に着地 → **ログイン済みの生徒なら**着席登録（`CheckInForm`：席種選択）／入室中なら `InRoomActions`（席移動・退室）／別校舎入室中なら警告。
- 退室はアプリ内（`check-out` ページ / `InRoomActions`）。閉室時刻で**自動退室**（`auto-checkout` Cron）。
- データ: `StudyRoomSession`（campus / seatType / checkInAt / checkOutAt / autoCheckedOut / pointAwarded）。

**変更要望（★要具体化）**: 「導線を変えたい」の具体像が未確定。想定される方向性：
- **(A) 入退室トグルQR**: 1つのQRで、未入室なら入室・入室中なら退室と自動判定（現状は入室QRのみで退室はアプリ内）。
- **(B) 座席単位QR**: 席ごとにQRを貼り、席種/席番号まで自動確定。
- **(C) 受付キオスク方式**: 校舎の端末で**生徒個人のQR**を読む（生徒のスマホログイン不要化）。
- **(D) ログイン不要打刻**: スキャンだけで本人識別（トークン付きQR等）。運用は楽だが**なりすまし対策**の検討が要る。

**要確認**: 上記のどれ（複数可）か。特に「**生徒のログインを介す現状**を維持するか、ログイン不要にしたいか」が設計の分岐点。

**オーナー記入**：導線変更にいたった経緯は、生徒がQRリーダーアプリを使う場合、システムを開くブラウザとQRアプリから開くブラウザが一致しないのでログインを毎度しないといけないためでした。なのでログイン後の生徒がQRを挟まず自習室利用や移動の登録を行える必要があります。具体的には生徒のメニューに自習室利用登録のUIを追加することです。

## ④ 講師のポイント評価精度追加

**現状**: **講師の評価/ポイント機構は存在しない**。`PointTransaction` は**生徒**の自習室ポイント（+1付与/−N交換）専用。「精度追加」という表現から、既存の何らかの講師スコアを指している可能性もあるが、コード上は見当たらず。

**解釈候補（★要意図確認）**:
- **(A) 講師評価制度の新設**: 勤怠・タスク遂行・面談数などの**実績を客観指標としてポイント化**し、講師を評価する。既存データで算出可能な素材：`Attendance`（勤怠実績）/ `Task`（遂行・要引き継ぎ処理）/ `Meeting`（面談数）/ 引き継ぎ受領数。
- **(B) 既存の主観評価に客観指標を足して"精度"を上げる**: 管理者の手動評価に上記実績を加味。
- **(C) 生徒ポイント付与の講師関与**: 講師が生徒ポイントを評価付与する仕組みの精緻化。

**要確認**:
1. 「評価」の**目的**（人事評価／表彰／シフト最適化の入力）。
2. **評価者**（管理者のみ？相互評価？）と**評価対象指標**。
3. 「ポイント」は**講師に付くスコア**か、生徒ポイント運用の話か。

> この項は前提が最も不明確。方針決めの短い確認を先にするのが安全。

**オーナー記入**：この件こちらが指定するのではなく評価ポイントをいくつも提案してほしくて、その中から採用するものをこちらで選び、ポイントを付与する形で評価したいです

## ⑤ 大学の受験情報更新を追跡する

**目的**: 大学ごとの入試情報（学部/方式/日程/科目/定員/偏差値目安 等）を保持し、**年度更新・募集要項改定を追跡**する。①②の基盤データにもなる。

**現状**: 大学データは**無し**。既存の `School`/`SchoolEvent` は生徒の**在籍高校**とその行事用で別物。

**仕様案**:
- **大学マスタ** `University`（name / 所在地 / 区分[国公私] 等）。
- **入試情報** `UniversityAdmission`（universityId / 学部・学科 / 方式[一般/共テ利用/推薦] / 試験日 / 出願期間 / 科目 / 定員 / 偏差値目安 / 受験料 / 対象年度）。
- **更新追跡**: 変更履歴 `AdmissionRevision`（差分・改定日・出所）か、`updatedAt` ＋更新ログで「いつ何が変わったか」を残す。重要更新は担当講師へアラート（既存 `Alert` を利用）。
- **要確認（★"追跡"の定義が二通り）**:
  1. **情報源**: 手動登録（運営が入力）か、外部（大学公式/入試ポータル）から**自動収集**か。
  2. **"追跡"の意味**: 手動更新の**差分履歴管理**（内部運用）か、外部情報の**変更検知・監視**（自動）か。後者はスクレイピング/AI要約＋定期実行（Cron）の設計になる（Hobbyプランの Cron 2本制限に注意）。
  3. 対象範囲（生徒の志望校のみ / 主要大学網羅）。

  **オーナー記入**：昨今のAI発展などで大学側が受験方式を変えたり、科目を変えたり、色々やってくるんですが、各大学のHPにしか情報が乗りません。それを拾って通知してほしいのです。集めたデータは大学や受験科目などで検索できるようにしてほしいですね。

## ⑥ 生徒自身の入退室記録を見れるように

**目的**: 生徒が自分の自習室の入退室履歴（と累計ポイント）を確認できるようにする。

**現状**: `/study-room` は `requireAuth(["admin","teacher"])` で**生徒はアクセス不可**。生徒が自分の `StudyRoomSession` 履歴を見る画面が無い。

**仕様案**:
- 生徒向けページ（例 `/study-room/history` または `/account` 配下）に、自分の入退室履歴を一覧表示：日時・校舎・席種・**滞在時間**・自動退室フラグ。
- 併せて**累計ポイント**と内訳（`PointTransaction`）も表示できると自然（現状ポイントは admin 画面のみ）。
- データは自分の `studentId` に限定して取得（サーバーコンポーネント or 専用API）。既存 `StudyRoomSession` をそのまま参照、スキーマ変更不要。
- **要確認**:
  1. 表示範囲（期間フィルタ・月次合計滞在時間などの集計要否）。
  2. **ポイントも同画面**に出すか、履歴のみか。
  3. 置き場所（自習室配下 or アカウント/ダッシュボード）。

> 7件中もっとも独立・低リスク。単独で先行実装しやすい。

## ⑦ 教材マスタの追加

**目的**: 現在バラバラに自由記述されている「教材」を**マスタ化**し、選択式にして表記ゆれを解消。総ページ数からの残量/ペース計算にも活用。

**現状（教材が自由記述で散在）**:
- `ProgressRecord.material`（教材名・自由記述）
- `LearningGoal.materialName` / `BigGoal.materialName`（目標の教材名・自由記述）
- `PrintUnit`/`StudentPrint`（ゼミ用プリント。教材とは別系統だが近接概念）

**仕様案**:
- **教材マスタ** `Material`（subject / name / publisher? / totalPages? / level[textbook/chart 等] / 有効フラグ）。
- 進捗入力・学習目標フォームで教材を**マスタから選択**（フリー入力は補助として残すか要検討）。
- マスタの `totalPages` を使えば、`LearningGoal.targetPages` や進捗ペース（1日何ページ）の算出が精緻化。
- **移行**: 既存の自由記述 `material` / `materialName` をマスタへ寄せる（名寄せ）方針の要否。
- **要確認**:
  1. マスタの**必須項目**（総ページ・出版社・レベルを持つか）。
  2. 既存自由記述データの**移行方針**（一括名寄せ / 併存 / 新規のみマスタ）。
  3. `PrintUnit`（ゼミプリント）と**統合するか別管理**か。

**オーナー記入**：目標や面談記録を記入するときにマスタから選択できるように変更もしないとね。
