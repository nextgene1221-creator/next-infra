## 0. 既存ファイルとの関係

このプレイブックは既存ファイルを生かして書かれている。**運用情報を二重持ちしない** こと。各ファイルの役割は §6 を参照。

| 用途 | 参照先 |
|---|---|
| 仕様（正） | `spec.md`（リポジトリルート）。画面別詳細は `juku-system/docs/01〜08_*.md` |
| 修正指示リスト（進行中 / 完了） | `docs/todo.md` |
| バックアップ基盤の積み残し | `docs/backlog.md` |
| 直近の作業状態（今何をしているか / セッション特例ルール） | `docs/current-task.md` |
| オーナー判断窓口 | `docs/questions-for-owner.md` |
| 自動ログ（**手動編集不可**） | `CHANGELOG_AI.md`（Stop hook `.claude/hooks/log-changelog.mjs` が生成） |
| 仕様同期ルール / Next.js 注意 | `juku-system/CLAUDE.md` / `juku-system/AGENTS.md` |
| バックアップ手順 / LINE 設定手順 | `docs/backup.md` / `docs/line-setup-request.md` |

### タスクの粒度分担（重要）

- `docs/todo.md` = オーナーからの **修正指示単位**（番号付き。完了したら「完了」へ移動し番号を振り直し、コミットハッシュを記録）
- 本ファイル §5 = **横断的・中期のロードマップ**（todo.md に載らない品質・運用・基盤の課題）
- `docs/current-task.md` = **いま手を動かしていること**（1画面で現在地がわかる状態を保つ）

同じタスクを 2 箇所に書かない。迷ったら「オーナーが指示した修正 → todo.md」「リーダーが自発的に積んだ課題 → playbook §5」。

## 1. 役割と原則

- **プロジェクトリーダーとして指揮を取る**。方向決定・レビュー運営・タスク更新に責任を持つ。
- **完成・安定運用に向けたタスクリスト (§5) を更新し続ける**。進捗反映、新課題追加、優先順位 (P0/P1/P2) 再評価。
- **スコープ削減・機能縮小は原則行わない**。
  - Red Team が削減提案を出した場合は **原則不採用** とし、`docs/questions-for-owner.md` にオーナー判断送りで記録する。
  - 例外: セキュリティ・法務上「実装すると違法レベル」の場合のみ即削減し、事後にオーナー報告。
- **オーナー判断は待たない**。`docs/questions-for-owner.md` にデフォルト判断を併記して記録し、その判断で実装を進める（覆されたら戻す）。ただし §3 の「オーナー判断送り」に該当するものは勝手に方向転換しない。
- **オーバーリーチ禁止**。方針転換・スコープ縮小・外部費用発生・本番データへの破壊的操作はオーナー判断送り（§3）。
- **各項着手前に不明点を確認する**（`docs/todo.md` 冒頭ルール）。曖昧なまま実装しない。
- **完了報告は実態に基づく**。「実装完了」と書くのは §8 のローカル検証を通してから。未検証なら「実装済・未検証」と正確に書く。

### 修正指示の受領フロー（必須・2026-08-18 追加）

オーナーから修正指示を受けたら、**いきなり実装に入らない**。次の順で進める。

1. **指示を `docs/todo.md` の「進行中」に項目として登録**する（番号付き）。
2. **理解と対応方針をまとめたファイルを作成する** — `docs/understanding-YYYY-MM-DD.md`。各項について以下を書く:
   - 指示の**解釈**（何をどう変えると読んだか）
   - **現状**（既存の実装・スキーマ・画面がどうなっているか。実際にコードを読んで確認した事実）
   - **対応方針**（変更するファイル、スキーマ変更の有無、マイグレーションの要否、UI の変化）
   - **確認が必要な点**（仕様が一意に決まらない箇所。選択肢とデフォルト案を併記）
   - **影響範囲・リスク**（既存データ、権限、他機能への波及）
3. **オーナーの確認を取る**。ここで仕様理解のズレを潰す。
4. 確認が取れてから **§2 発注前チェックリスト → 実装 → §8 ローカル検証** に進む。

目的: 「実装してから仕様が違うと分かる」手戻りを無くすこと。規模の大きい指示ほど厳守する。

### push / コミットの標準ルール

- 標準は **各項完了後に中間報告 → コミット → push**（`docs/todo.md` 冒頭ルール）。
- ただし **オーナーはセッション単位でこれを上書きできる**（例:「今回は push せずローカル検証まで」）。
- セッション特例が指示されたら、**必ず `docs/current-task.md` の冒頭に明記**してから作業に入る。特例は明示的に解除されるまで有効。

## 2. 評価委員会（6視点）

単一塾向けの業務システムという性質に合わせて定義したもの。

| 視点 | 見る観点 |
|---|---|
| **塾長・運営** | 校舎運営として回るか、講師のオペ負荷、既存業務フローとの接続、費用 |
| **講師** | 日々の入力負荷、導線の短さ、面談・シフト・進捗記録の実務 |
| **生徒・保護者** | わかりやすさ、モチベーション、保護者への説明可能性、未成年への配慮 |
| **エンジニア** | データ構造 (Prisma/Neon)、マイグレーション安全性、パフォーマンス、保守性 |
| **セキュリティ・個人情報** | **未成年の個人情報**、ロール権限の境界、認証、LINE 連携、外部送信（AI へのデータ投入含む） |
| **Red Team** | 反論役。「そもそも要るか」「壊れる筋」を潰す |

- **Red Team は必ず最終ラウンドで通す**。
- 発動粒度は **実装の発注単位 / 修正指示 1 項目単位** で再判定する（フェーズ単位でまとめて素通ししない）。

### 発注前チェックリスト（verbalize してから着手する）

1. 新規 UI 画面・導線を含むか → **講師 / 生徒・保護者** 必須
2. 権限・データ構造（`juku-system/prisma/schema.prisma` / migration）の追加変更か → **エンジニア / セキュリティ** 必須
3. 校舎の運用フロー・オペレーションに影響するか → **塾長・運営** 必須
4. 外部連携を触るか（LINE / AI Gateway / Vercel Blob / Cron / GitHub Actions） → **セキュリティ / エンジニア** 必須
5. 小さな実装変更か → **Red Team のみ**で可
6. バグ修正・リファクタか → スキップ可

**委員会 2 視点以上が「前提条件付き」または「法務・個人情報リスク」を指摘したら、即時着手せず Q を立てて待機する。**

## 3. オーナー判断送り vs デフォルト判断

「後から覆すコストが large か?」を判定基準とする。

### オーナー判断送り（`docs/questions-for-owner.md` に記録。デフォルト判断は明示しつつも、方向転換は勝手にしない）

- 方針転換（スコープ縮小、フェーズ順序入替、機能の取り下げ）
- **外部費用が新規発生**（Vercel プラン変更、AI トークン枠拡大、LINE の有料メッセージ枠、Neon 容量追加）
- **個人情報・法務**（未成年の情報の扱い、保護者同意、成績・面談記録を外部 API に送る判断）
- **本番 DB (Neon) への破壊的マイグレーション**、データ削除、リストア
- **本番環境の設定変更**（Vercel env、LINE 実チャネル、Webhook URL、Cron 追加）
- Red Team が「実装するなら設計再考」レベルの反論を出したケース

### デフォルト判断で進める（判断ログを残しつつ実装）

- 既定スコープ内の設計詳細（テーブル名、API 形状、UI 配置、文言）
- バグ修正、保守、リファクタ
- 委員会レビューで意見が一致した変更
- ドキュメント整備、スモークスクリプト追加
- 開発 DB (`prisma/dev.db`) 上での実験・シード

迷ったら **影響範囲 large = 送り、small/medium = デフォルト判断で進める**。

## 4. /loop の運用と自己停止条件

### 起動

`/loop <interval> <prompt>` で定期実行。標準プロンプトは下記を毎回回す:

> 進捗確認＋ルール点検: (1) `docs/questions-for-owner.md` の新着回答取込 (2) 進行中の判断に §2 の該当視点が通っているか (3) 現場（塾長・講師・生徒）が実際に使えるか再点検 (4) `docs/current-task.md` の方針との整合性、セッション特例（push 可否など）の確認 (5) 止まっていたら次の作業に進める（ただし §4 自己停止条件を先に判定）

### 自己停止条件（どれか満たしたらループを停止し待機モードへ）

1. **3 ループ連続で「指示なし & 自走可能タスクなし」** — context 浪費なので停止
2. **全タスクが blocked-on-owner** — 未回答が溜まり、デフォルト判断で進められるタスクが残っていない
3. **方針転換を伴う Red Team 反論があり、オーナー判断送りにした直後** — 勝手に方向転換しない
4. **型チェック / Lint / ビルドが赤い状態が 3 ループ連続** — 自走で直せていない、人間判断要請
5. **本番 DB・本番環境への操作が必要になった時点**（§3 該当）
6. **オーナーから「停止」「待機」の明示指示**

停止時はオーナーに「停止理由」「待機中の判断項目」「再開トリガー」を 1 メッセージで伝える。

## 7. セッション再開手順

terminal 再起動・`/clear` 後・別 thread 移行などで「playbook に従って進めて」と言われたら、以下の順で読み込む:

1. **本ファイル (`docs/playbook.md`)** — 進行手順とタスクリスト把握
2. **`docs/current-task.md`** — 直近の作業状態と **セッション特例（push 可否など）** を復元
3. **`docs/questions-for-owner.md`** — 回答済みを取り込み、デフォルト判断との差分を確認
4. **`docs/todo.md` の「進行中」節** — オーナー指示の現在地
5. (必要時) **`spec.md`** / **`juku-system/docs/0*.md`** / **`CHANGELOG_AI.md` の末尾**

読み込み後、以下の順で行動:

1. `docs/todo.md` 進行中 → §5 の順で **未着手の最優先タスク** を選定
2. §2 発注前チェックリストを verbalize して必要レビュアーを決定
3. §3 に従い、オーナー判断送りなら `docs/questions-for-owner.md` に記録（デフォルト判断併記）
4. 実装後は **§8 のローカル検証を必ず通す**
5. ループ運用中なら §4 自己停止条件を毎回判定

## 8. ローカル検証手順（push 前に必ず通す）

作業ディレクトリは `juku-system/`。

| # | 内容 | コマンド | 必須 |
|---|---|---|---|
| 1 | 型チェック | `npx tsc --noEmit` | ★必須 |
| 2 | Lint | `npm run lint` | ★必須 |
| 3 | 本番ビルド | `npm run build`（`prisma generate` + `next build`） | ★必須 |
| 4 | スモークテスト | `npx tsx prisma/smoke-*.ts`（該当機能がある場合） | 該当時 |
| 5 | 実機 UI 確認 | `npm run dev` → ブラウザで導線をなぞる | UI 変更時 |

### DB の扱い

- 開発は `prisma/dev.db`（better-sqlite3 アダプタ）、本番は Neon。
- `juku-system/prisma/schema.prisma` を変更したら **マイグレーションを作成し、まず開発 DB で適用**する。
- **本番 Neon への適用は §3 の「オーナー判断送り」**。勝手に流さない。適用したら `docs/todo.md` に適用済みと明記する。

### 報告の粒度

- 1〜3 が全部緑になって初めて「実装完了」と書いてよい。落ちたら落ちた出力ごと報告する。
- 実機 UI 未確認なら「実装済・ブラウザ未確認」と正確に書く。

## 9. 教訓ログ

新しい教訓は時系列で追記する。

- **2026-08-18 プレイブック新設**: これまで運用書がなく、`docs/todo.md` の冒頭 4 行だけがルールだった。セッションをまたぐと運用ルール（着手前確認・完了後 push・spec 同期）が毎回失われていた。本ファイルと `docs/current-task.md` / `docs/questions-for-owner.md` を新設し、ルート `CLAUDE.md` から常時参照させる形にした。
- **2026-08-18 「完了・push 待ち」表記の腐敗（想定より広範だった）**: `docs/todo.md` 進行中 A が「実装完了・push 待ち／未コミット」のまま残っていたが、実際は `e6e3ccc`（6/24）・`5f05be2`（7/2）で**コミット済み・push 済み**だった。さらに**完了リストの 24〜30 も全て `commit 未` のまま**で、実際には全て push 済みだった（7 項目を実ハッシュに訂正）。
  - 原因: 実装した回に todo.md を先に書き、コミット後に戻って更新していない。**コミットが状態表記より後に来る運用では必ず腐る**。
  - 対策: 各項完了時に **コミット → そのハッシュを todo.md に書く** 順序を守る（§1 push ルール）。加えて §7 の再開手順で「進行中の表記と git 履歴が一致するか」を毎回突き合わせる。
  - **状態表記は実態と突き合わせて更新しないと嘘になる。**
- **2026-08-18 アカウント切替の落とし穴**: 別プロジェクトを別アカウントで作業した後、`gh` のアクティブアカウントと Git Credential Manager の資格情報が残り push が失敗する。また `vercel login` はブラウザのセッションが残っていると **確認画面を素通りして同じアカウントで再認証される**（CLI 側の logout だけでは切り替わらない）。アカウント切替時は「ブラウザ側のログアウト」までがワンセット。
- **2026-08-28 本番 DB (Neon) の compute time 枯渇で全機能停止**: 「システム内ログインに失敗する」という症状で発覚。実体は NextAuth ではなく **Neon が HTTP 402 (`Your account or project has exceeded the compute time quota`) で全クエリを拒否**していたこと。`authorize()` が DB 例外で `null` を返すため、画面上は「メール/パスワードが違います」に見えていた。ログインだけでなく DB を触る全機能（生徒一覧・出退勤・給与計算・日次バックアップ）が同時に停止していた。
  - 原因: `MeetingAlertPoller` が **60 秒ごと**に `/api/alerts/check-all`（DB クエリ 20 本超のバッチ処理）を叩いており、これが**認証レイアウトに置かれていたため生徒 60 名を含む全ユーザーの全タブから**走っていた。タブが 1 つでも開いていれば Neon の compute が自動サスペンドに入れず、Free プランの compute time（月約 190 時間）を使い切る。
  - 対応: オーナーが Neon を有料プランへアップグレード（即時復旧）。ポーリング間隔を **60 秒 → 5 分**に緩和（commit `46f9a61`）。
  - **残る設計上の問題**: 「全クライアントが同じバッチを叩く」構造自体は変えていない。人数が増えるほど無駄が増え、複数タブが同時に同じアラートを生成する競合リスクもある。本筋は `check-all` を Cron 側へ移すこと。
  - 教訓: **サーバーレス + 従量課金 DB では「クライアント発のポーリング」がそのまま課金と可用性のリスクになる**。定期実行はサーバー側（Cron）に置き、クライアントからは「読むだけ」にする。
