## B-1. 出願思考を生徒項目に追加

### 解釈
生徒プロフィールに「国公立志向か私立志向か」を表す単一選択項目を追加する。選択肢は 5 段階:
`国公立のみ` / `できるだけ国公立` / `どちらでもよい` / `できるだけ私立` / `私立のみ`

### 現状
- `Student` モデルに該当項目なし。近い項目として `considerRecommendation`（推薦検討）`track`（文理）がある。
- 生徒項目を 1 つ追加すると、実測で **以下 9 ファイル**に手が入る（`considerRecommendation` の出現箇所で確認）:
  - `prisma/schema.prisma` ＋ 新規マイグレーション
  - `src/app/api/students/route.ts`（新規作成）/ `src/app/api/students/[id]/route.ts`（更新）/ `src/app/api/signup/student/route.ts`（サインアップ）
  - `src/app/(authenticated)/students/[id]/edit/page.tsx`（編集フォーム）
  - `src/app/(authenticated)/students/[id]/page.tsx`（詳細表示）
  - `src/app/(authenticated)/account/profile/page.tsx`（本人プロフィール表示）
  - `src/app/signup/student/page.tsx`（サインアップフォーム）
  - 出願戦略・志望校コンサル AI の 4 ルート（プロフィールに含める場合）

### 対応方針
- `Student.applicationPolicy String @default("") @map("application_policy")` を追加。値は英語キーで保持し、表示はラベル変換する（既存の `track` / `gender` と同じ流儀）。
  - `public_only` / `prefer_public` / `either` / `prefer_private` / `private_only`
- 既存生徒は空文字（＝未設定）。必須にはしない。
- 編集フォーム・サインアップフォーム・詳細画面・本人プロフィールに `<select>` を追加。
- B-3 の AI プロンプトに「出願思考」として渡す。

### 確認事項
- **(a)** 未設定の既存生徒の扱い。デフォルト案 = 「未設定」を選択肢に持たせ、AI には「未設定」と渡す（勝手に「どちらでもよい」に丸めない）。
- **(b)** サインアップフォーム（生徒が自分で登録）にも出すか。デフォルト案 = **出す**。

### 影響範囲
既存データへの破壊なし（`@default("")` で追加）。本番 Neon へのマイグレーション適用は playbook §3 によりオーナー判断送り。

## B-3. 出願戦略 AI のプロンプト変更

### 解釈
沖縄の受験生が主対象なので、**国公立の出願を基本形**とする。具体的に 4 点:

1. 国公立は **前期・中期・後期の 3 パターン**で出す
2. それとは**別枠**で私立の候補も出す
3. **挑戦 / 実力相応 / 安全（滑り止め）** の区分を、**国公立と私立で別々に**出す
4. **「伸ばしたい項目」を削除**

### 現状（`src/app/api/admin/ai-test/strategy/route.ts`）
- 出力スキーマの `plan[]` は `tier: "本命" | "併願" | "滑り止め"` の 3 値のみ。**国公立/私立の区別も、前期/中期/後期の区別も持っていない**。
- プロンプトは「本命・併願・滑り止めのバランス」を指示している。
- 沖縄前提の遠征費・宿泊費試算（`DEFAULT_AIRFARE=40000` / `DEFAULT_LODGING=8000`）は既に実装済み。
- `UniversityAdmission` には `method`（一般/共通テスト利用/推薦…）はあるが、**前期/中期/後期の日程区分カラムはない**（`method` か `examDate` の文字列に混ざっている可能性が高い）。

### ⚠️ 指示の文言について（要確認）
- **確認 (a)**: 「**調整**、実力相応、安全（滑り止め）」の「調整」は **「挑戦」**（チャレンジ校）の変換ミスと解釈しました。この解釈で合っていますか。デフォルト案 = **「挑戦 / 実力相応 / 安全」**。
- **確認 (b)**: 「伸ばしたい項目を削除」の対象について。**「伸ばしたい科目」は出願戦略（②）ではなく、志望校コンサル（①）の出力項目です**（`src/app/api/admin/ai-test/route.ts` の `weakSubjects`、画面表示は `AiTestClient.tsx:318`）。出願戦略側には該当項目がありません。
  - デフォルト案 = **① 志望校コンサルの「伸ばしたい科目」(`weakSubjects`) を削除する**。
  - ①ではなく②の別の項目（`risks` や `advice` 等）を指している場合はご指定ください。

### 対応方針
出力スキーマを組み替える（`strategySchema`）:

```
plan → 廃止し、以下に置き換え
  publicPlan:  { 前期: [...], 中期: [...], 後期: [...] }   // 国公立
  privatePlan: [...]                                        // 私立（別枠）
各校の項目に tier: "挑戦" | "実力相応" | "安全" を持たせる
```

- 国公立側は日程区分（前期/中期/後期）× tier（挑戦/実力相応/安全）で構成。
- 私立側は tier のみで構成（日程区分は私立にないため）。
- プロンプトに「国公立を基本とし、前期・中期・後期の 3 パターンを必ず提示する」「私立は別枠で提示する」「tier は国公立・私立それぞれで独立に判定する」を明記。
- B-1 の出願思考・B-2 の志望校立地をプロフィールに追加して渡す。
- 表示側 `AiTestClient.tsx` の出願戦略セクションを新構造に合わせて作り直す。会話継続用の `strategyToText()` も更新。
- ① の `weakSubjects` を削除（確認 (b) が取れたら）: `route.ts` のスキーマ・`AiTestClient.tsx` の表示・`consultToText()` の 3 箇所。

### 確認事項
- **(c)** 中期日程は実施校が非常に少ない（公立大の一部のみ）。候補が無い場合の挙動。デフォルト案 = **「該当なし」と明示して空で返す**（無理に埋めない）。
- **(d)** 私立側にも「共通テスト利用」を区分として分けるか。デフォルト案 = **分けない**（各校の `method` に文字列で持たせる）。
- **(e)** 各区分に何校ずつ出すか。デフォルト案 = **国公立は前期/中期/後期それぞれ挑戦・実力相応・安全から各1校程度、私立は挑戦・実力相応・安全で各1〜2校**。

### 影響範囲
スキーマ変更なし。AI 出力の構造が変わるため画面と会話継続テキストの両方を直す必要がある。結果は保存していない（`// 結果は保存しない` とコメントあり）ので過去データの移行は不要。

## B-4. ゼミ管理: 誤って完了したプリントを取り消せるように

### 解釈
プリントを誤って「完了」にしてしまった場合に、完了状態を解除できるようにする。

### 現状
- **API 側は既に対応済み**。`PUT /api/student-prints` は `completedDate: null` を受け取ると完了を解除する実装になっている（`data.completedDate = completedDate ? new Date(completedDate) : null`）。
- **UI 側で塞がれているだけ**。`SeminarManager.tsx` で:
  - `openEdit()` が `if (p.completedDate) return;` で完了済みを弾く
  - マトリクスのセルが `isClickable = !p?.completedDate` で完了済みをクリック不可にしている
- つまり**完了にしたら UI からは二度と触れない**状態。

### 対応方針
- 完了済みセルもクリックできるようにし、モーダルを開けるようにする。
- モーダル内に **「完了を取り消す」ボタン**を追加 → `PUT { id, completedDate: null }`。
- 完了済みの場合はモーダルの表示を切り替える（「完了にする」は隠し、「完了を取り消す」を出す。予定日編集は完了中は不可のまま）。
- 誤操作防止のため確認ダイアログを 1 枚挟む。

### 確認事項
- **(a)** 取り消せる権限。デフォルト案 = **講師・管理者のみ**（生徒は不可）。生徒にも許可する場合はご指定ください。
- **(b)** 完了取り消し後の予定日。デフォルト案 = **元の `scheduledDate` を保持したまま**（完了フラグだけ外す）。

## B-5. 講師・管理者のダッシュボード / ゼミ管理に当日プリントを表示し、そこから完了登録

### 解釈
当日予約されているプリントを、番号・必要枚数（同じプリントを予約している人数）付きで表示し、**その画面から完了登録もできる**ようにする。

### 現状
- **表示は既に実装済み**。`dashboard/page.tsx` の「本日使用するゼミプリント」カード（503〜531行）に、
  **科目 / 単元 / No. / 必要枚数 / 対象生徒** の表があり、単元×No で集計して人数を出している。合計枚数と種類数も表示済み。
- **足りないのは「完了登録」の部分だけ**。現在はサーバーコンポーネントの読み取り専用テーブル。
- ゼミ管理画面 (`/seminar`) 側には当日集計ビューが**ない**（生徒×プリントのマトリクス表示のみ）。

### 対応方針
- 当日プリントのカードをクライアントコンポーネントに切り出す（例 `TodayPrintsPanel.tsx`）。
- 各行を展開すると**対象生徒が個別に並び、生徒ごとに「完了」ボタン**を置く → `PUT /api/student-prints { id, completedDate: today }`。

- 同じコンポーネントを `/seminar` にも設置し、ダッシュボードとゼミ管理で同じ当日ビューを共有する。
- 集計クエリは既存ロジックを流用するが、完了登録に `studentPrint.id` が要るため `grouped` に **id を持たせる**必要がある（現在は生徒名しか持っていない）。

### 確認事項
- **(a)** 一括完了（その行の全員をまとめて完了）を用意するか。デフォルト案 = **用意する**（「全員完了」ボタン。運用上まとめて配って回収するはず）。→印刷や用意の完了を指しているわけではなくプリントの実施を完了と指しています。なのでここで完了とすればそのゼミ予約自体が完了となる
- **(b)** 現在このカードは**未完了のみ**（`completedDate: null`）を表示している。完了済みも見えた方がよいか。デフォルト案 = **完了済みも薄く表示**（何枚刷ったかの根拠が消えると困るため）。→デフォルト案でよし
- **(c)** ゼミ管理画面のどこに置くか。デフォルト案 = **既存マトリクスの上に「本日のプリント」セクションとして追加**。→それでOK

## B-9. 給与計算機能を追加

### 解釈
講師と管理者に**時給**を設定し、**出退勤の記録から毎月の給与明細を発行**できるようにする。

### 現状
- 出退勤は `Attendance`（`teacherId` / `clockIn` / `clockOut` / `campus`）で記録済み。
- `/attendance` 画面には**既に月次集計のロジックがある**（`monthStart` / `monthEnd` で絞って一覧化）。勤務時間の算出基盤はある。
- **時給の項目はどこにもない**（`Teacher` にも `User` にもなし）。給与・明細のテーブルもなし。
- 管理者は `User.role = "admin"` で、`Teacher` レコードを持つとは限らない → **「管理者にも時給」を実装する場所が問題になる**（下記 確認 (a)）。

### 対応方針（案）
```
model HourlyWage {        // 時給（履歴を持つ。昇給に対応）
  id, userId, hourlyYen, effectiveFrom, createdAt
}
model Payslip {           // 給与明細（確定させて保存）
  id, userId, yearMonth, totalMinutes, baseYen, adjustmentYen, totalYen,
  status(draft/confirmed), confirmedAt, ...
  items PayslipItem[]
}
model PayslipItem {       // 明細の内訳（日次）
  id, payslipId, date, minutes, hourlyYen, amountYen, note
}
```
- 月次で `Attendance` を集計 → 明細を**下書き生成** → 管理者が確認して**確定** → 表示・印刷。
- 時給は履歴テーブルにして、`effectiveFrom` で当時の時給を引く（過去の明細が昇給で変わらないように）。
- 画面: `/payroll`（管理者）＝ 月選択・一覧・確定、`/payroll/me`（本人）＝ 自分の明細閲覧。

### 確認事項（**設計判断が多いので実装前に解消したい**）
- **(a) 管理者の時給をどこに持つか**。管理者は `Teacher` レコードを持たない場合がある。デフォルト案 = **`User` に紐づける**（`HourlyWage.userId`）。講師・管理者の両方を同じ仕組みで扱える。→OK
- **(b) 端数・締め**。デフォルト案 = **分単位で集計し、月合計の分数 × 時給 ÷ 60 で計算、円未満切り捨て**。締めは月末。→OK
- **(c) 深夜・残業・交通費**。デフォルト案 = **今回は実装しない**（時給 × 時間のみ）。必要なら `adjustmentYen`（手動調整）で吸収。→OK
- **(d) 打刻漏れの扱い**（`clockOut` が null のレコードが実在しうる。`forgotClockOutAlerted` フラグがある）。デフォルト案 = **明細生成時に警告として一覧表示し、その日は 0 分として集計**（勝手に補完しない）。→OK、管理側から修正できるしね
- **(e) 明細の出力形式**。デフォルト案 = **画面表示＋ブラウザ印刷（`window.print()`）**。PDF ライブラリは新規に入れない。→OK
- **(f) 給与額の閲覧権限**。デフォルト案 = **本人と管理者のみ**。他の講師の額は見えない。→OK
- **(g)** 過去分の遡及計算をするか。デフォルト案 = **時給を設定した月以降のみ**。→する

### 影響範囲・リスク
- **給与額は誤ると実害が出る**。playbook §2 のセキュリティ視点（閲覧権限）と、エンジニア視点（端数処理・タイムゾーン）を必ず通す。
- 集計は JST 基準で行う必要がある（`clockIn` は UTC 保存）。既存 `/attendance` の実装に合わせる。

## B-10. 発行する QR コード等すべてに「外部ブラウザで開く」URL パラメータを追加

### 解釈
QR リーダー専用アプリの内蔵ブラウザで開かれるとログインセッション（Cookie）が引き継がれず、読み取っても使えない。そこで **URL に外部ブラウザで開かせるパラメータを付ける**。

### 現状
- QR を発行しているのは **1 箇所のみ**: `src/app/(authenticated)/study-room/CheckInQR.tsx`
  - URL は `${origin}/study-room/check-in?campus=<校舎>`
  - 校舎ごとに発行し、拡大・印刷して掲示する運用。
- 他に `qrcode.react` を使っている箇所はない（grep で確認）。
- 退室用 `/study-room/check-out` は画面としては存在するが、**QR は発行していない**。

### 対応方針
- QR に埋める URL へ `?openExternalBrowser=1` を付与する。
  - これは **LINE の内蔵ブラウザを外部ブラウザに切り替える公式パラメータ**。この塾は LINE 連携を本番稼働させており（`docs/todo.md` A フェーズ3）、生徒が LINE 経由で開くケースが想定されるため実効性が高い。
- QR コンポーネントを共通化し、URL 生成を 1 箇所に集約する（`lib/qrUrl.ts` のようなヘルパー）。今後 QR を増やしても付け忘れないようにする。
- 表示している URL 文字列・印刷面にも同じ URL を出す。

### ⚠️ 重要な限界（確認事項）
- **(a)** `openExternalBrowser=1` は **LINE 内蔵ブラウザにのみ有効**な独自パラメータです。**汎用の QR リーダーアプリには効きません**（そのアプリ独自の設定に依存し、URL 側から強制する標準的な方法は存在しない）。
  - つまりこの対応だけでは「QR リーダー専用ブラウザでログインが引き継がれない」問題は**完全には解決しません**。
  - 補完案（デフォルト案）: **未ログインで `/study-room/check-in` に来たら、ログイン後に元の URL へ戻す**（`callbackUrl` 付きでログイン画面へ誘導）。これなら内蔵ブラウザでもログインさえすれば着席登録まで到達できる。
  - **どちらを実装しますか。デフォルト案 = 両方**（パラメータ付与＋ログイン後リダイレクト）。→両方
- **(b)** 「QR コード等すべて」の「等」に含めたいものがあれば教えてください。現状 QR は上記 1 箇所のみです。管理者イントロダクションのサインアップ URL も対象にする場合はご指定ください（コード上で URL を生成している箇所は見つかりませんでした）。→ごめんない
